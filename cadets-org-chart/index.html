Cadets Org Chart - Build Guide

A single SharePoint list drives a Power Fx-rendered org chart for all 108 posts across 10 departments — real structure and colours extracted directly from the source PDF's own geometry, never from reading names. This page was rebuilt from scratch to reflect that finished design, rather than the exploratory phase-by-phase proof that got here: earlier drafts had Command running its own bespoke tree-layout algorithm and five departments in the wrong shape entirely, both since corrected. Command is now a plain grid department like the other nine, and the two Power Automate flows that used to compute its layout live have been retired — every post's position is now a literal, Python-seeded value, self-healing per department the same way it always has for the other nine.

What This Page Is

Build reference for the Cadets Org Chart canvas app (local project: C:\Users\Phaderon\Projects\PowerApps-Apps\cadets-org-chart). Everything on this page reflects the current, correct design — not a history of how it got here. That history (five departments' real shapes discovered wrong, a full render-formula rewrite, Command folded into the grid, two flows retired) lives in the project's own dated build log if you ever need it, not here.

Data protection, stated plainly: post titles, reporting lines, categories and colours are structural data, extracted only from the source PDF's card shapes/positions and connector lines — never from reading any name. OccupantName is the one field with people's actual names in it, and it's yours to fill in directly in SharePoint; the shipped data file seeds it with entirely fictional placeholder names (not modelled on anyone real) purely so the chart doesn't render empty.

Architecture At A Glance

  • One SharePoint list, OrgChartPosts, is the only data store — 108 rows, one per post. See Data Model below for every column.
  • One Power Fx formula builds the whole chart as a single SVG string, shown in one Image control. It reads OrgChartPosts, works out each department's row position live from its actual current headcount (so the canvas grows — never shrinks, never collides — as people are added), and draws every card, connector, and the one peer-line, in one pass. See Current State for the complete formula.
  • No Power Automate flows in production. Every post's FinalX/FinalY/Width is a literal, Python-seeded value — true for 9 of the 10 departments from the start, and now true for Command too, since it no longer needs its own bespoke branching-tree layout. The two flows that used to compute Command's layout live (OrgChart - Compute Depth, OrgChart - Compute Width & Position) have been retired.
  • One more flow is planned, not built: a PDF export flow, the only Power Automate piece left in the design. See PDF Export.

Data Model - OrgChartPosts

108 rows. Every column added via +Add column, never Excel import — see SharePoint Setup for why.

ColumnTypeMeaning
TitleText (built-in)Post ID, e.g. CMD-201, SG-106. Seeded, not edited.
ManagerPostIDTextThe real reporting relationship — whose post this one reports to. Seeded.
SortOrderNumberSibling order under the same manager. Seeded.
PostLabelTextRole title shown on the card. Seeded.
DepartmentTextWhich of the 10 department panels this post belongs to. Seeded.
CategoryTextPersonnel category (Regular, Civil Servant, FTRS, etc.) — drives card colour. Seeded; provisional for gapped posts (see Real Department Structure).
DeptBaseX / DeptBaseYNumberEach department's own anchor point. DeptBaseY is 0 for every department — the live row-start Y is added on top at render time, not stored here. Seeded.
DepthNumberHow many reporting steps below the department head this post sits. Seeded — drives card height (34px at Depth 0, 27px otherwise).
WidthNumberThis post's own card width. Seeded.
FinalXNumberAbsolute horizontal position on the whole canvas. Seeded, literal.
FinalYNumber (plain, not Calculated)Vertical offset from this post's own department panel top (0-based). The render formula adds the live row-start Y on top. Seeded, literal.
RelationshipTypeTextSolid (default) or Dotted — describes the connector line's own style. Only one post uses Dotted so far.
PeerPostIDTextA lateral, non-hierarchical link to another post's Title — used once, for Media & Comms' two co-equal leads.
VisualParentPostIDTextWho the connector line is drawn from — either exactly equal to ManagerPostID (a connector is drawn), or blank (no connector drawn at all). Blank specifically for any peer stacked below the first in its column: several different direct reports of one manager, stacked to save space, all genuinely report to that manager in parallel — drawing a line from each to the one physically above it would look like they report to each other, which they don't. The first card in the stack still connects to the real lead/head; being grouped in the same column conveys the rest.
IsGappedYes/NoTicked for a vacant post. The card greys out, gets a dashed border, and shows "GAPPED" instead of a name — the role title still shows. Category stays whatever it's set to underneath (a placeholder until filled).
OccupantNameTextThe person's name. Blank for gapped posts. Yours to fill in or correct directly in SharePoint — the shipped data seeds fictional placeholders, never real names.

Category colours

Rebuilt 2026-09-17 for legibility. The PDF's own legend colours included a hot pink, a pure yellow and a saturated orange that were genuinely unreadable behind the grey occupant-name text — the worst pairing measured 3.1:1, a WCAG 2.2 AA failure. Every fill is now a pastel of roughly even lightness, the occupant-name grey is darkened from #6B7A8D to #46545E, and no two fills sit closer than 11.4 ΔE so they stay tellable apart.

This diverges from the source PDF deliberately. If the printed chart is ever expected to match the original document's legend colour-for-colour, that is a conversation to have first — the trade was made for accessibility, on the basis that an unreadable name is worse than a colour that has shifted.
Gapped posts' Category is a best guess (the most common category in that post's own column), not a real fact — the PDF's grey/dashed styling tells us a post is vacant, not what category it should be once filled. Treat every IsGapped = Yes row's Category as provisional until someone real is assigned.

SharePoint Setup

One-time setup for this version of the schema — ~15 minutes

  1. If OrgChartPosts already has rows from an earlier build, delete them all — this version's data fully replaces any previous set.
  2. Add three new columns via +Add column (never "Create list from Excel" — it mangles internal field names, a confirmed, repeated finding in this project): RelationshipType (Text), PeerPostID (Text), VisualParentPostID (Text).
  3. If FinalY exists as a Calculated column from an earlier build, delete it and re-add it as a plain Number column — it's a literal seeded value now, the same as FinalX and Width already are.
  4. Confirm OccupantName (Text) and IsGapped (Yes/No) already exist — add them the same way if this is a fresh list.
  5. Add one new column first: CardH, type Number, via + Add column — not by importing, so it keeps a clean internal name. It carries each card's height, worked out at build time from whether a post's siblings branch across columns or stack in one. Without it every card renders blank-height.
  6. Download OrgChartPosts_Data_v17.xlsx (see Downloads) and bulk-paste all 108 rows into the list's Quick Edit grid view, matching the sheet's own column order exactly. Quick Edit only inserts values into already-existing columns, so it can't trigger the same field-mangling problem "Create list from Excel" does.
  7. If the two old flows are still imported in your environment — OrgChart - Compute Depth (Production) and OrgChart - Compute Width & Position (Production) — delete or turn them off. Nothing in the current design calls either one any more.

PDF Export — via Print(), not PDF()

Superseded design, 2026-09-16 — the original PDF()+flow approach is abandoned; see why below

Why this changed: the original design used the experimental PDF() function to build a Blob and pass it to a flow that saved it into SharePoint automatically, no save dialog. In real Studio testing, every export came out visibly blurred — and crucially, the blur was completely insensitive to DPI, Size, or making the source control 2–3× larger. That ruling-out is what proved the problem: real vector/SVG content stays sharp when displayed bigger (confirmed — the on-screen chart at any zoom was "beautifully crisp"), so a fixed blur regardless of source size means the rasterization is happening inside PDF()'s own internal capture step, before your Size/DPI values are ever applied. This matches how screenshot-style/headless PDF generators generally behave (confirmed against real technical writeups on SVG-to-PDF rasterization) — only a genuine browser print pipeline reliably preserves vector quality, because it renders content through the same engine as on-screen display rather than capturing a bitmap first. Conclusion: PDF() is not fit for this chart while it remains an experimental, screenshot-style function. Switched to Power Apps' Print() function instead — older, non-experimental, and confirmed to use the real browser print pipeline. Real trade-off: Print() can't hand the app a file to pass to a flow, so the one-click "auto-saved to SharePoint" flow is gone — the person exporting saves the PDF themselves from the print dialog and uploads it to SharePoint by hand, the same way they would without any of this.

The OrgChart - Export PDF flow and its importable zip (see Downloads) are no longer used by this design — harmless to leave imported and unused if you already did.

Design

  1. Build a dedicated screen, e.g. scrChartPrint, used only for printing — nothing else on it. Set that screen's own Width to 1450 and its own Height to varRowCY + 30 + varRowCH + 10 + 36 + 10 (the exact same total-height formula the chart's own SVG viewBox uses). This is what fixes the large blank space at the bottom of the export: Print() prints the whole screen, blank space included, so the screen's own size has to match the chart's real content size rather than the app's general-purpose screen resolution.
  2. Put one Image control on scrChartPrint (Image property: "data:image/svg+xml," & EncodeUrl(varChartSvg), same as the main chart), with Width/Height both set to Parent.Width/Parent.Height so it fills the screen exactly — no letterboxing, no leftover blank space.
  3. On your main screen, add the button that takes you to the print view. Insert → Button, name it btnOpenPrintView, set Text to "Export to PDF", and set OnSelect to: Navigate(scrChartPrint, ScreenTransition.None)
  4. On scrChartPrint, add two buttons — one that actually prints, one to get back out again:
    • btnDoPrint — Text: "Print / Save as PDF", OnSelect: Print()
    • btnBackFromPrint — Text: "Back", OnSelect: Navigate(scrMain, ScreenTransition.None) — swap scrMain for whatever your main chart screen is actually called
  5. Hide both of those buttons while printing, or they will appear in the PDF. Set each button's Visible property to: Not scrChartPrint.Printing
    Printing is a real built-in screen property (documented in Microsoft's own Print() reference) that is true only while the print dialog is being prepared — so both buttons show normally on screen, then disappear from the printed output.
Why two buttons instead of one — and what the good pattern actually is. The tempting version is a single button doing Navigate(scrChartPrint, ScreenTransition.None); Print(). Don't: Power Fx gives no guarantee that the destination screen has finished rendering before the next statement in the chain runs, so Print() can fire against the screen you just left. The good pattern is exactly what steps 3–5 above describe — one button navigates and stops there, and a separate button living on the destination screen calls Print(), by which point the person is demonstrably already on that screen. Two clicks rather than one, and the person gets to eyeball the print view before committing to it.
Two things confirmed directly against Microsoft's own Print() reference (learn.microsoft.com/en-us/power-platform/power-fx/reference/function-print), not guessed: Print() takes no arguments at all — it always prints whichever screen the calling button lives on, not a specific control, which is why the design above uses a dedicated screen rather than trying to target the chart directly. And in the browser's print dialog, "Background graphics" must be ticked (Chrome: "More settings") or the coloured department headers/panels print as plain white — a real, documented gotcha, not a guess.
Margins in the print dialog. The chart is width-bound on A3, so it always fills the full printable width — any white band down the sides is the page margin, not the chart falling short. Chrome: More settings → Margins → None widens the printable area from 1134pt to 1191pt and prints everything about 5% larger (scale 0.782 → 0.821). Note: Allan tried this and still got a margin, so the setting does not appear to fully take effect in every browser or PDF driver — worth trying, but do not count on edge-to-edge output. The banner and footer are rounded partly so that a bar which stops short of the paper edge still reads as deliberate.
Known limitation, not yet solved: the browser print dialog does not reliably remember paper size ("A3") or the "Fit to printable area" scale option between exports — there is no Power Fx property that controls this, it's entirely the browser's own print-dialog behaviour. If it's not sticking for you, that's not something this design can currently force. One partial mitigation: set your Windows default printer to "Microsoft Print to PDF" so at least the destination doesn't need reselecting each time, even if paper size/scale still do.

Not yet confirmed: whether sizing the dedicated screen exactly to content removes the "nothing shows until Fit to printable area" symptom Allan saw on the first real test (expected to help significantly, since the mismatch between screen size and paper size was likely a big part of it, but not independently re-tested since this redesign).
