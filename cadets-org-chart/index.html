Cadets Org Chart - Proof & Build Guide

Replacing the manually-maintained Visio branch org chart (108 posts, 10 departments, 5 vacancies) with a Microsoft-only, SharePoint-list-driven Power Apps chart. Phases 0-2 are confirmed passed — the Image-control-renders-generated-SVG approach genuinely works, including at real department scale. Current stage: combining all 10 departments into one full-sheet render, still on local data, before any SharePoint schema or editing screens are built.

What This Page Is

Working proof log for the Cadets Org Chart canvas app (local project: C:\Users\Phaderon\Projects\PowerApps-Apps\cadets-org-chart — no separate GitHub/screen-YAML repo yet, this project hasn't reached real screens). Full brief, the four-page mockup PDF and the separate interactive HTML concept live in that project's docs/handoff/ folder.

Why this starts with a proof, not a build: the Power Apps Bible has zero prior lab-verified experience with a computed SVG in an Image control, or with Print()/A3 export — this is genuinely new ground for this app family, not a known-working pattern being reapplied. Phase 0 below is the cheapest possible test of the riskiest assumption.

The algorithm, in plain terms — "subtree-width reservation." Every leaf card reserves a fixed 150px slot. Next Steps

Phases 0-3 are all confirmed passed, including Command's layout rework. Deliberately staying on local hardcoded data for as long as possible before introducing SharePoint — every question left below is answerable without it, and the brief's own phasing puts the data layer last for exactly that reason.

  1. Phase 4 — Automated Tree Layout Proof (CONFIRMED PASSED, then redesigned twice). Proved Power Fx can compute a simple tree's layout live from a ManagerPostID field. Verified directly against the real Cadets Branch Structure chart, though, that "simple" isn't enough — Safeguarding alone has two 6-person teams side by side, which Phase 4's fixed-width packing is proven (deliberately, via its own stress test) to collide on. A correct, zero-overlap, provably-minimal algorithm for this has been worked out and verified — just not in Power Fx (see next step).
  2. Phase 5 — Power Automate Depth Proof (not yet run). Pivoted the hard part of the layout algorithm out of Power Fx entirely, onto Power Automate + SharePoint, since a flow has real loops and variables that Power Fx's non-recursive formula chain doesn't. This phase tests only the smallest, riskiest new piece — can a flow walk a manager chain and write the answer back — before attempting the full collision-avoiding layout in a flow. The single riskiest open technical question in the project right now.
  3. If Phase 5 passes — build the full layout algorithm as a flow. Every department becomes the same kind of automatically-laid-out tree Command already is, computed by a flow whenever the SharePoint list changes, with Power Apps only ever reading pre-computed X/Y columns and rendering — not computing anything itself. Information Systems' full depth/squads/dotted-lines was confirmed a fringe case, not needed generally.
  4. Colour legend/key (not started, but the hard part already works). colCategoryColours is already the single source of truth every card's colour reads from — changing one row's Hex already recolours every matching card everywhere, with no other change needed. What's actually missing is a rendered key/legend on the sheet itself, reading from that same table, so it never falls out of sync with the cards. Small, low-risk, worth doing whenever colour work resumes.
  5. Real A3 Print() test (not started). First test anywhere in this Bible of Print()/A3 export.
  6. Real-length label stress test (not started). Swap the mockup's shortened labels for full-length real post titles (occupant names stay illustrative/placeholder, not real staff, per the brief) to check nothing wraps or clips at true production text lengths.
  7. Interactive "explore" screen (later, separate from the print sheet). An Image control has no clickable sub-regions — confirmed back in Phase 0, still true. A click-to-expand experience needs real Power Apps galleries/buttons as a second screen sharing the same ManagerPostID data, not a change to this SVG rendering.
