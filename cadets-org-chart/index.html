Cadets Org Chart - Proof & Build Guide

Replacing the manually-maintained Visio branch org chart (108 posts, 10 departments, 5 vacancies) with a Microsoft-only, SharePoint-list-driven Power Apps chart. Current stage: proving a Power-Fx-generated SVG in an Image control can actually reproduce the approved mockup design, before any SharePoint schema or editing screens are built. Nothing below has been run in Power Apps yet — tick each phase off only once you've genuinely run it and it matches.

What This Page Is

Working proof log for the Cadets Org Chart canvas app (local project: C:\Users\Phaderon\Projects\PowerApps-Apps\cadets-org-chart — no separate GitHub/screen-YAML repo yet, this project hasn't reached real screens). Full brief, the four-page mockup PDF and the separate interactive HTML concept live in that project's docs/handoff/ folder.

Why this starts with a proof, not a build: the Power Apps Bible has zero prior lab-verified experience with a computed SVG in an Image control, or with Print()/A3 export — this is genuinely new ground for this app family, not a known-working pattern being reapplied. Phase 0 below is the cheapest possible test of the riskiest assumption.

Phase 0 - Static SVG Sanity Test

Blank throwaway canvas app · ~5 minutes · tests the riskiest assumption in isolation

Does Power Apps' Image control accept a computed SVG data URI at all, in your actual MOD tenant? Neither this Bible nor Policy Tracker's has ever tried it — everything downstream depends on this primitive working. Test A is hand-typed, no Power Fx string-building. Test B does the same thing via a formula, to separate "does SVG render" from "does string concatenation survive."

  1. New blank canvas app (tablet, any format — throwaway, delete after). Insert → Image, resize to roughly fill the screen.
  2. Set the Image control's Image property to this complete formula (note the pre-escaped %23 in place of literal # — this test also proves whether that matters):

  1. Set the Image control's Image property to =varCommandDataUri. Add a second button (e.g. btnToggleMode) whose OnSelect is:
btnToggleMode.OnSelect — flips the mode AND re-triggers the render button v1 · 2026-09-11 09:47 BST 
Set(varChartMode, If(varChartMode = "Quiet", "Coloured", "Quiet"));
Select(btnRender)
btnRender here must be your render button's actual control name (tree view / Properties dropdown), not its display Text — easy to mix up if both buttons happen to show the same caption. Why this line is needed at all: varCommandDataUri only changes when its own Set() runs. Flipping varChartMode alone doesn't make anything else recompute — nothing in Power Fx reactively reruns a different Set() formula just because a variable it reads has changed. Skip the Select() line and the toggle button will appear to lag one click behind: pressing it does nothing, and the next press of the render button shows the flip instead.
CONFIRMED PASSED, 2026-09-11 (screenshot on file, both colour modes). Concat/With/LookUp resolved category colour correctly per-row, not collapsed to one value across every card. Vacant XO rendered dashed/grey with GAPPED, and Branch Administrator still visibly connects to it underneath — the hard-requirement case. Both colour modes matched the Visual Spec section above. The toggle-button lag above was the one real gap, and it's a wiring issue, not a rendering one — now fixed and logged in known-bad-patterns.md as a reusable pattern for this whole app family.

Next Steps (Not Started)

From the original brief, once Phases 0-2 above are confirmed:

  1. Layout and print with the actual structure — real 108 posts (not mockup labels), full page-grid layout across all 10 departments (only Information Systems' internal column packing is proven so far), a real Print() A3 test, a defined legibility/overflow threshold.
  2. Data and editing — SharePoint schema (PostID, ReportsToPostID, TeamID, OccupantName/person reference, PersonnelCategory, OccupancyStatus, display order), validation (cycles, missing parents, duplicate IDs), permissions at the data layer, not just hidden controls.
  3. Delivery and evidence — acceptance tests (fill vacancy, vacate-with-child, change category, move reporting post, long labels, invalid/cyclic relationship, full record count, both styles, real A3 export) become real once the data layer exists.

Known Limitations / Open Questions

  • Only Command (hand-placed) and Information Systems (one department, computed grid) are drafted. The other 8 departments and the full-page composition (all panels together, per the measured page grid) are not yet built.
  • Corner radius on cards is visually estimated (~3pt), not numerically confirmed from the PDF's path data.
  • Print()'s documented restrictions (no mobile, no multi-page, browser print-to-PDF only) haven't been tested against a real full-page render yet.
