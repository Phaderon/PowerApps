Fix 1 - Block Saving Personal OneDrive Links As Document Links

ViewItem · property edit · no risk

The Open In App icon-scan already looks for the real SharePoint document-library domain (modgovuk.sharepoint.com) on OpenDesktop_2.Visible. A personal OneDrive share link (e.g. https://modgovuk-my.sharepoint.com/:w:/r/personal/...) uses a different domain — the -my.sharepoint.com "my site" domain, not the document library — so it was never going to be recognised, and worse, it's not something colleagues should be linking to from a tracked policy item anyway (personal OneDrive isn't shared storage). First attempt used a toast on Save, but toasts are easy to miss. Replaced it with a persistent inline text block under the URL field itself (reusing the existing error-label spot, so it shows live as soon as the link is typed/pasted, not just on Save). Save itself still re-checks the same condition independently as a fallback — it doesn't just rely on the label being visible, so even if the inline warning were somehow not showing, Save would still silently refuse to submit a personal OneDrive link.

  1. Open ViewItem.
  2. In the Tree view, find ErrorMessage29_2 (the small text under the "Direct URL to document" field).
  3. Select Text in the Properties dropdown, select all, and replace with this formula.
ErrorMessage29_2.Text 
If(
    "modgovuk-my.sharepoint.com" in Lower(DataCardValue29_2.Text),
    "This is a personal OneDrive link. Please save this document into SharePoint first, then paste the SharePoint link here.",
    frmLink_2.Valid = false && !IsBlank(frmLink_2.Error),
    "URL is required.",
    ""
)
  1. Still on ErrorMessage29_2, select Wrap in the Properties dropdown and set it to true (the message is longer than the old "URL is required." text, so it needs to wrap onto a second line instead of being cut off).
  2. Now find btnSaveLink_2 (the Save button in the same modal). This is the fallback check — it runs the same domain test again independently, so Save still refuses to submit even if the inline warning above wasn't showing.
  3. Select OnSelect in the Properties dropdown, select all, and replace with this formula.
btnSaveLink_2.OnSelect 
If(
    !varSubmitting && !("modgovuk-my.sharepoint.com" in Lower(DataCardValue29_2.Text)),
    Set(varSubmitting, true);
    SubmitForm(frmLink_2);
    // Do NOT refresh here
    Set(varSubmitting, false)
)
Test: paste a modgovuk-my.sharepoint.com/:w:/r/personal/... link into the URL field — the warning text should appear straight away under the field, wrapped onto two lines, and hitting Save should do nothing while it's showing. A normal modgovuk.sharepoint.com document-library link should show no message and still save as before.

Fix 2 - "Save Failed / Invalid URL Value" On Address-Bar Document Links

ViewItem · property edit · no risk

Reported urgent 2026-07-29: adding a document link failed with a pink "Save failed" banner and a briefly-flashed SharePoint error, PolicyLinks failed: Invalid URL value. A URL field contains invalid data. Confirmed via issue #33 comparison: a link copied from the browser's address bar while viewing a Word doc in Office Online (323 characters, carrying Outlook tracking junk like &clickparams=..., &CID=..., &wdLOR=...) failed every time, while the same file's proper Share > Copy Link (169 characters) saved fine. The SharePoint LinkUrl column has its own length cap and rejects anything over it with exactly this error — it has nothing to do with the file type or which website the link points to (a bare domain like google.com with no http:///https:// scheme will also be rejected by SharePoint, for a separate, unrelated reason). The existing Update formula on this field already trimmed one known junk parameter (&action); extended it to also trim the three new ones seen in this report, so the link still saves with its real share token intact, just without the extra tracking noise pushing it over the length limit.

Known limitation, not fixed by this: links copied from the address bar this way don't contain the filename anywhere in the URL (just an opaque ID token), so their document-link icon will still show generic rather than picking up the real file type. That's a limitation of what that link format contains, not something a formula can fix. Using Share > Copy Link remains the better habit for a correct icon too.
  1. Open ViewItem.
  2. In the Tree view, find LinkUrl_DataCard2_2 (the data card wrapping the "Direct URL to document" field).
  3. Select Update in the Properties dropdown, select all, and replace with this formula.
LinkUrl_DataCard2_2.Update 
With(
    {
        fullUrl: DataCardValue29_2.Text
    },
    If(
        IsBlank(fullUrl),
        Blank(),
        Left(
            fullUrl,
            Min(
                If(Find("&action", fullUrl) > 0, Find("&action", fullUrl) - 1, Len(fullUrl)),
                If(Find("&clickparams", fullUrl) > 0, Find("&clickparams", fullUrl) - 1, Len(fullUrl)),
                If(Find("&CID=", fullUrl) > 0, Find("&CID=", fullUrl) - 1, Len(fullUrl)),
                If(Find("&wdLOR", fullUrl) > 0, Find("&wdLOR", fullUrl) - 1, Len(fullUrl))
            )
        )
    )
)
Test: open a Word/Excel doc in Office Online from a link inside Outlook, copy the address bar URL, paste it into "Direct URL to document" and hit Save — it should save without error now. A normal Share > Copy Link URL should still save exactly as before (nothing in this formula changes for URLs that don't contain those tracking parameters).

Fix 3 - Hint Text For The Generic-Icon Limitation

ViewItem · new label · no risk

Follow-up to Fix 2: even after the save crash is fixed, links copied from the browser address bar still show a generic document icon instead of the real file type, because GetFileExt() (in Formulas.txt) can only detect a file type from a file= query parameter or a dotted extension right before a ? in the URL path — and the compact address-bar link format contains neither, just an opaque ID token. There's no reliable way to recover the real filename from that token without an extra Microsoft Graph lookup (e.g. a Power Automate flow resolving the share link), which was judged not worth the extra infrastructure for a cosmetic icon. Decided instead to just tell people, clearly, right where they're about to paste the link.

  1. Open ViewItem.
  2. In the Tree view, find Activator_1 (the "No document links yet" empty-state group, containing Label6_2, lblLinkFieldsHint1, btnAddLinkEmpty1, and SVG_13).
  3. Add a new Label control as the last child of Activator_1, named lblLinkCopyHint1, with the properties below.
lblLinkCopyHint1 (new Label@2.5.1) 
Align: Center
AutoHeight: true
Color: RGBA(91, 105, 97, 1)
Font: Font.'Open Sans'
Size: 9
Text: ="Tip - use Share > Copy Link on the document, not the browser address bar. Address bar links still save, but the app can only show the correct file icon when copied this way."
Width: 380
Wrap: true
Test: open an item with no document links yet — the new tip text should appear under the "+ Add Document Link" button, wrapped onto multiple lines, without affecting anything else in that empty-state block.
